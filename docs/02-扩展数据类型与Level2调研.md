# 股票图表组件 · 扩展数据类型与 Level2 数据调研（第二期）

> 调研日期：2026-11-15
> 承接：`01-历史行情数据格式调研.md`（第一期，只覆盖主图 K 线/分时的 OHLCV）。
> 本期范围：组件要包含**主图 + 多副图**（成交量、成交额、量比、MACD 等），并支持**筹码峰、集合竞价、交易明细（Level2，含 B/S/C）**，仍以「查看历史」为目标。
> **术语约定**：本文统一用「**逐笔明细**」指代两类数据 —— ① 交易所 Level-2 的原生逐笔数据（如深交所 STEP `UA202` 报文），毫秒级、单向单笔；② 公开接口返回的 3 秒合并分笔。两者粒度不同，组件侧以 `granularity: 'tick' | 'merged3s'` 区分，不可混用。
> 本文为技术调研，不含任何投资建议。

> **文档定位与现状说明**
> 本文为第二期扩展数据调研，需求矩阵与公开接口实测为当时结论。当前 `chips` 由 `bars` 在运行时派生（不再预计算静态 JSON），`pane` 一词按 `docs/00` §7 读作 Module / Region。概念定义以 `docs/00` 为准。

## 0. 结论先行

1. 本轮需求可归为三类数据，获取难度完全不同：

   | 类别 | 包含 | 获取难度 |
   |---|---|---|
   | **A. OHLCV 派生** | 成交量、成交额、MACD、KDJ、RSI、BOLL、OBV 等副图 | 低：第一期的数据已够，前端算即可 |
   | **B. 建模衍生** | 筹码峰（成本分布） | 中：**不是交易所数据**，只能拿统计指标或自己按算法算 |
   | **C. L2 原生** | 逐笔明细/委托、十档盘口、委托队列、集合竞价 | 高：交易所历史 L2 需授权采购，公开接口只给 3 秒合并分笔 |

2. **大部分副图不需要新增数据**：MACD/KDJ/RSI/BOLL/CCI/DMI/OBV 全部只依赖 OHLCV；真正需要额外输入的只有 4 个 —— **量比**（需前 5 日分钟量）、**换手率**（需流通股本）、**资金流/主力净流入**（需逐笔 BS + 金额分档）、**筹码峰**（需历史 K 线 + 换手率 + 流通股本）。
3. **筹码峰不是交易所 L2 字段**，上交所/深交所行情接口说明书里根本没有这个数据项，因此**没有官方标准格式**。它是行情终端基于历史成交与换手率建模估算的衍生指标，不同软件结果可以不同。可得的只有两种形态：按日的统计指标（获利比例、平均成本、成本区间、集中度），或自行计算的价格档直方图（常见 150 档）。
4. **「B/S/C」不是一个统一字段，绝不能全局套用**。它在沪市成交、沪市委托、深市成交、深市委托标识串、以及各家公开接口里含义各不相同；`C` 在通达信深市标识串里是**撤单**，在另一些 CSV 方案里是撤单类事件，而沪市撤单用 `OrdType='D'`，集合竞价成交则**不打 B/S 标志**。详见第 5.3 节对照表。
5. **Level2 历史数据是重量级数据**：上交所逐笔委托单日约 12 GB、逐笔明细单日约 6 GB，A 股高频全市场每日增量 30 GB+（DolphinDB 教程，属二手来源需核实原文）。前端组件**不能全量加载**，必须按「标的 × 交易日」切片、服务端预聚合、明细按需分页 + 虚拟滚动。
6. **公开 HTTP 接口给的不是真 L2 逐笔**：东财/腾讯的明细是 **3 秒合并分笔**（一条含多笔成交），与交易所逐笔明细（毫秒/百分之一秒、单向单笔）不是一个粒度。做「交易明细」副面板时必须在 UI 与数据模型上区分这两种口径。
7. 组件架构上要多引入 3 种 pane 类型：**普通副图**（共享 x 轴）、**筹码峰**（与主图共享价格 y 轴的横向柱状图）、**集合竞价**（独立 9:15–9:25 时间轴）；交易明细则是与 crosshair 联动的虚拟滚动表格。

## 2. 副图指标的数据依赖与计算输入

| 指标 | 输入 | 计算要点 |
|---|---|---|
| 成交量 / 成交额 | `volume` / `amount` | 直接画，注意单位统一为「股 / 元」 |
| MACD | `close[]` | `EMA12 - EMA26 = DIF`，`DEA = EMA9(DIF)`，`MACD = 2×(DIF-DEA)` |
| KDJ / RSI / BOLL / CCI / DMI | `high[] low[] close[]` | 纯 OHLCV 派生 |
| OBV | `close[] volume[]` | 收盘涨则加量、跌则减量 |
| **量比** | 当日累计成交量 + 前 5 交易日每分钟均量 + 当日已开市分钟数 | 定义：开市后每分钟平均成交量 ÷ 过去 5 个交易日每分钟平均成交量。常用算法 `量比 = 现成交总手 / (过去5日平均每分钟成交量 × 当日累计开市分钟数)`。**需要至少 5 日历史分钟/日量数据**；集合竞价量与盘后量是否计入需按口径统一 |
| **换手率** | `volume` + 流通股本 | `换手率 = 成交量(股) / 流通股本 × 100%`；流通股本是随增发/解禁变化的**时间序列**，不能只存一个静态值 |
| **振幅** | `high low preClose` | `(high-low)/preClose × 100%` |
| **资金流 / 主力净流入** | 逐笔明细 `side` + 单笔成交额 | 按单笔金额分档（如小/中/大/超大单），`B` 计入流入、`S` 计入流出、`N/M/C` 中性不计；**集合竞价成交无主动方向，必须排除** |

> 副图通用契约建议：所有指标输出统一为 `{ paneId, name, series: {time, value}[], style, precision }`，这样新增副图不需要改主图数据链路。

## 3. 筹码峰（成本分布）

### 3.1 它不是标准数据

上交所《历史数据接口说明书 v1.1.2》与深交所 STEP 规范的字段表中**均无筹码分布字段**。它是行情软件基于历史成交与换手率建模估算的衍生指标，因此：

- 不存在跨平台「标准字段」；
- 通达信/同花顺/东财/大智慧的计算结果可以不同（获利盘比例差几个百分点属正常）；
- 常见算法为**三角形成本分布 + 历史衰减系数设为 1**，早期筹码不衰减，与真实换手存在系统性偏差；
- 大宗交易、转融通、限售解禁、ETF 申赎造成的筹码转移不一定进入模型。

### 3.2 可得的两种数据形态

**形态 A：按日统计指标**（AkShare `stock_cyq_em` 一类接口返回，来源为第三方文档与示例，需核实原文）

| 列 | 含义 |
|---|---|
| 日期 | 交易日 |
| 获利比例 | 当前价之下筹码占流通盘比例（0~1） |
| 平均成本 | 累计 50% 筹码处的价格（中位数成本） |
| 90成本-低 / 90成本-高 | 去掉两端各 5% 后的价格区间 |
| 90集中度 | `(高-低)/(高+低)`，越小越集中 |
| 70成本-低 / 70成本-高 | 去掉两端各 15% 后的价格区间 |
| 70集中度 | 同上 |

> 注意列名存在版本差异：有版本写 `90集中度` / `70集中度`，也有写 `90聚焦度` / `70聚焦度`，接入前必须打印 `columns` 做映射。

**形态 B：完整筹码峰直方图**（前端真正画「峰」需要这个）

```ts
interface ChipHistogram {
  date: string;
  prices: number[];   // 常见 150 档价格，价格域均分（精度下限 0.01 元）
  ratios: number[];   // 各档筹码占流通盘比例，总和 ≈ 1
}
```

第三方实现（如 stock-sdk `chips`）公开的东财 CYQCalculator 口径（**二手来源，需核实原文**）：

- 价格域均分 **150 档**；
- 逐日先把存量筹码 `× (1 - 换手率)` 衰减；
- 再把当日换手筹码按**三角形分布**铺到 `[low, high]`，顶点在均价 `(O+C+H+L)/4`；
- 一字涨停/跌停堆入单一价格档；
- `WINNER(X)`（价格 X 处获利盘比例）与 `COST(N)`（N% 筹码获利的最低价）互为反函数；
- 回看窗口默认 120 根 K 线（与东财 App 一致），`range=0` 为上市首日全量累计。

### 3.3 组件设计要点

- 筹码峰是**横向柱状图**，x 轴是筹码占比、y 轴是价格，必须与主图 K 线**共享价格轴并同步缩放**；
- 颜色区分获利盘 / 套牢盘，进阶可做时间分层（火焰山：5 日内 / 5 日前 / N 日内）；
- 若做成「历史某日的筹码峰」，需要按该日截断计算，**不能只存最新一天的直方图**；
- 复权口径会影响筹码分布：切换前/后复权时应重算或禁止切换；
- 数据依赖：历史日 K（含换手率）+ 流通股本 + 除权除息事件，建议在服务端/构建期预计算成静态 JSON，前端只消费直方图。（当时建议；现状运行时由 `bars` 派生）

## 4. 集合竞价

### 4.1 交易所一手格式（上交所）

来源：上交所《历史数据接口说明书 v1.1.2》（2023-12-13），历史 L2 数据为 CSV、UTF-8、逗号分隔、换行 `0x0A`，目录 `sh2\yyyymmdd\`。

`Auction.csv`（开盘集合竞价，**仅覆盖 2018-12-24 之前**的全部证券；之后改由 `Snapshot.csv` 发布；收盘集合竞价数据包含在 L2 行情快照中）：

| 字段 | 含义 | 说明 |
|---|---|---|
| `SecurityID` | 证券代码 | STRING |
| `DateTime` | 日期时间 | NUMBER，如 `20151123091630` |
| `Price` | 成交价 | NUMBER(3) |
| `VirtualAuctionQty` | **虚拟匹配量** | 按该价位的预计成交量 |
| `LeaveQty` | **虚拟未匹配量** | 未撮合余量 |
| `Side` | **匹配情况** | `0` 无未匹配量 / `1` 买方有未匹配量 / `2` 卖方有未匹配量 |

> `Side` 不是买卖方向，而是「未成交余量落在哪一侧」，极易误读。

快照 `PhaseCode` 第 1 位标识交易阶段：`S` 启动（开市前）/ `C` 集合竞价 / `T` 连续交易 / `B` 休市 / `E` 闭市 / `P` 停牌 / `M` 可恢复熔断 / `N` 不可恢复熔断 / `D` 开盘竞价结束到连续竞价开始前。

### 4.2 公开接口形态

AkShare `stock_zh_a_hist_pre_min_em`（东财盘前分时，来源：AkShare 相关文档与示例，二手来源需核实原文）：

| 列 | 类型 | 说明 |
|---|---|---|
| 时间 | object | 从 `09:15` 开始 |
| 开盘 / 收盘 / 最高 / 最低 | float64 | 元 |
| 成交量 | float64 | **手** |
| 成交额 | float64 | 元 |
| 最新价 | float64 | 元 |

数据示例（来源同上，2021-08-27）：

```text
时间               开盘   收盘   最高   最低   成交量  成交额      最新价
2021-08-27 09:15  18.46 18.46 18.46 18.46 0      0.0        18.460
2021-08-27 09:16  18.46 18.79 18.79 18.46 0      0.0        18.460
...
2021-08-27 14:57  18.36 18.38 18.39 18.35 3243   5958328.0  18.586
2021-08-27 15:00  18.39 18.39 18.39 18.39 7522   13832958.0 18.584
```

> **竞价期间成交量为 0，价格是虚拟撮合价**，这与连续竞价分钟 K 的语义完全不同。前端不能用同一套 Bar 语义去画竞价段。
> 该接口只返回**最近一个交易日**的分钟数据（含盘前），不支持任意历史日 → 与第一期「历史分时深度不足」的结论一致。

### 4.3 建议的前端数据结构

```ts
interface AuctionPoint {
  time: string;              // 'HH:mm:ss'，9:15-9:25 或 14:57-15:00
  phase: 'open' | 'close';
  virtualPrice: number;      // 虚拟撮合价（竞价期间）
  matchedQty: number;        // 虚拟匹配量，手（lot）
  unmatchedQty: number;      // 虚拟未匹配量，手（lot）
  unmatchedSide: 0 | 1 | 2;  // 见 4.1
  volume: number;            // 实际成交量（竞价期间为 0，9:25 统一撮合后才有）
  amount: number;
}
```

> ⚠️ 集合竞价阶段的成交**没有明确主动方向，交易所不打 B/S 标志**。因此：竞价成交不能用于计算主力净流入；供应商若在竞价成交上打了 B/S（见 5.4 实测），那是其自行填充，需单独标记来源。
>
> **单位与现状口径**：本节为二期建议模型；当前 `auction_20261113.json` 落盘 `matchedQty` / `unmatchedQty` 单位为**手**（`manifest.units.auction.matchedQty='lot'`），与 `intraday.volume` 的**股**相差 100 倍，换算统一用 `LOT_SIZE`。落盘竞价仅 7 字段，`volume` / `amount` / `source` 等由 `deriveDataset()` 运行时补齐（详见 `docs/00` §3.4 与 `src/data/SOURCES.md`）。

## 5. Level2 交易明细、逐笔委托与 B/S/C

### 5.1 上交所历史 L2 CSV（一手字段）

来源：上交所《历史数据接口说明书 v1.1.2》（2023-12-13）。

**`Tick.csv` 竞价逐笔明细**：

| 字段 | 含义 | 口径 |
|---|---|---|
| `SecurityID` | 证券代码 | STRING |
| `TradeTime` | 成交时间 | NUMBER，如 `2015112309163002`，**精确到百分之一秒** |
| `TradePrice` | 成交价格 | NUMBER(3) |
| `TradeQty` | 成交量 | 股票：**股** |
| `TradeAmount` | 成交金额 | NUMBER(3)，**2023-06-01 起由 2 位精度改为 3 位** |
| `BuyNo` / `SellNo` | 买方 / 卖方订单号 | NUMBER |
| `TradeIndex` | 成交序号 | 2021-04-26 启用 |
| `ChannelNo` | 频道代码 | 2021-04-26 启用 |
| **`TradeBSFlag`** | **内外盘标志** | **`B` 外盘主动买 / `S` 内盘主动卖 / `N` 未知**，2021-04-26 启用 |
| `BizIndex` | 业务序列号 | 与逐笔委托合并后的连续编号 |
| `SendingTime` | 发送时间 | 2021-11-25 起 |

**`Entrust.csv` 竞价逐笔委托**（2021-04-26 启用）：`SecurityID`、`TransactTime`（`20150803093008000`，**毫秒**）、`Price`、`Balance`（委托数量）、`OrderBSFlag`（`B` 买单 / `S` 卖单）、`OrderNo`、`OrdType`（**`A` 新增 / `D` 删除**）、`OrderIndex`、`ChannelNo`、`BizIndex`。

**`Snapshot.csv` 十档快照**：`BidPrice[10]` / `BidOrderQty[10]` / `OfferPrice[10]` / `OfferQty[10]` / `NumTrades` / `InstrumentStatus` / `TradingPhaseCode` / `TotalVolumeTrade` / `TotalValueTrade` 等；快照间隔 3 秒或 5 秒，相邻相同快照只保留第一幅。

> 上交所**不用 `C` 表示撤单**，撤单通过 `OrdType='D'` 表达。且 `TradeBSFlag` 只在 **2021-04-26 之后**的数据中存在，更早的历史逐笔明细没有方向字段，需自行推断。

### 5.2 深交所 STEP（一手字段，差异极大）

来源：《深圳证券交易所 STEP 行情数据接口规范》。逐笔行情两种发送模式：模式一 `UA201`（逐笔委托）+ `UA202`（逐笔明细）；模式二合并到 `UBO01`（网关默认模式一）。

| 字段 | 取值 | 含义 |
|---|---|---|
| `ExecType` | `4` / `F` | **撤销 / 成交**（是成交类别，**不是买卖方向**） |
| `Side` | `1` / `2` / `G` / `F` | 买 / 卖 / 借入 / 出借（深市委托，数字非 B/S） |
| `OrdType` | `1` / `2` / `U` | 市价 / 限价 / 本方最优 |
| `MDStreamID` | `011` / `021` / `051` / `413` … | 现货集中竞价 / 债券回购 / 协议交易 / 点击成交等 |
| `ApplSeqNum` / `ChannelNo` | — | 消息记录号 / 频道代码 |

> **深市逐笔明细没有 B/S 主动性字段**。要判断主动方向，只能用「成交价 vs 当时买一/卖一」或「买方委托序号 + 委托价」回溯推断，且需与十档快照按时间戳对齐（快照 3 秒 vs 逐笔毫秒级、通道不同步，误差来源多）。

### 5.3 B/S/C 完整对照表（本期最重要结论）

| 场景 | 字段 | 取值 | 含义 |
|---|---|---|---|
| 沪市逐笔**成交** | `TradeBSFlag` | `B` / `S` / `N` | 外盘主动买 / 内盘主动卖 / **未知**（部分 SDK 把 `N` 注释为「集合竞价」，交易所原文是「未知」） |
| 沪市逐笔**委托** | `OrderBSFlag` | `B` / `S` | 买单 / 卖单（与主动性无关） |
| 沪市委托类别 | `OrdType` | `A` / `D` | 新增委托 / **删除委托（撤单是 D，不是 C）** |
| 沪市逐笔类型 | `Type` | `A` / `D` / `S` / `T` | 新增委托 / 删除委托 / 产品状态订单 / 成交 |
| 深市逐笔**成交** | `ExecType` | `4` / `F` | 撤销 / 成交（**不是方向**） |
| 深市逐笔**委托** | `Side` | `1` / `2` / `G` / `F` | 买 / 卖 / 借入 / 出借（数字，非 B/S） |
| **深市委托标识串**（通达信等终端的软件层约定） | 字符串 | `B` / `S` / **`C`** / `BS` / `CS` / `2B` / `VB` / `WB` / `XB` / `YB` … | `B` 买委托、`S` 卖委托、**`C` 撤单记录**、`BS` 委买撤单、`CS` 委卖撤单；其余为市价/最优五档/本方最优等特殊业务 |
| 腾讯公开逐笔明细 | 末位字母 | `B` / `S` / **`M`** | 主动买 / 主动卖 / **中性（实测）** |
| 东财公开逐笔明细 | `f55` 数字 | `1` / `2` | 方向数字码（**本次未取得官方映射说明，必须抽样验证**） |
| 集合竞价成交 | — | 无 / `N` / 供应商自填 | **交易所不打 B/S**，无明确主动方向 |

> 结论：**`C` 的含义随市场、供应商、表（成交表 vs 委托表）而变，绝不能全局套用**。归一化时应保留 `rawSide` 原始值 + `side` 统一值 + `sideSource` 来源说明三个字段。

### 5.4 公开接口实测（一手，2026-11-15，`sh600519` / `secid=1.600519`）

**东方财富 `push2/api/qt/stock/details/get`**（`fields2=f51..f55`）：

```text
"14:56:35,1432.97,34,16,1"
"14:56:38,1435.09,27,10,2"
"15:00:02,1435.26,1773,459,1"     ← 收盘集合竞价
"15:05:01,1435.26,4,6,1"          ← 盘后固定价格交易
```

位序：`时间, 价格, 成交量(手), 成交笔数, 方向码(1/2)`。特点：3 秒合并分笔；含盘后 15:05–15:30 明细；收盘集合竞价那笔也带方向码 `1`。

**腾讯 `stock.gtimg.cn/data/index.php?appn=detail&action=data`**：

```text
序号/时间/价格/涨跌/成交量(手)/成交额/BS标志
0/09:25:02/1404.00/0.00/150/21060000/S      ← 集合竞价
1/09:30:02/1403.10/-0.90/83/11646422/S
5/09:30:14/1394.43/0.37/79/11020889/M
6/09:30:17/1395.43/1.00/30/4186818/B
```

本次解析 70 条，方向分布 `S=26 / M=24 / B=20`。特点：也是 3 秒合并分笔；用字母 `B/S/M`，`M` 为中性；**09:25:02 集合竞价那笔被标成 `S`**，与「集合竞价不打 B/S」的交易所规则不同，属于供应商自行填充。

> 这两组一手样例直接证明：**同一市场、同一天，不同供应商对方向标记、集合竞价归属、中性盘的编码都不一样**。资金流类副图若混用数据源会失真。

### 5.5 数据量与前端加载策略

- 二手资料（DolphinDB 教程）给出量级：股票逐笔委托单日约 **12 GB**、逐笔明细单日约 **6 GB**，A 股高频全市场每日增量 **30 GB+**（基金债券等 45 GB+）；具体数字需核实原文，但量级结论明确。
- 因此「只看历史」的前端组件必须：
  1. 按 `symbol + tradeDate` **分片导出**，一次只加载一天、一个标的；
  2. 副图所需的**资金流/量比等指标在服务端预聚合**，前端只拿聚合结果；
  3. 逐笔明细表格用**分页 + 虚拟滚动**，不要一次性 `setData` 全部 tick；
  4. 区分「明细原始粒度」与「图表聚合粒度」，两者用不同接口与缓存策略。

## 6. 统一数据模型扩展（在第一章 `Bar` / `IntradayPoint` 之上）

> 本节为二期建议模型；当前对外契约见 `src/types.ts` 的 `ChartDataset`

```ts
/** 逐笔明细：归一化为统一语义，同时保留原始编码 */
interface TradeTick {
  timestamp: number;          // UTC 毫秒
  time: string;               // 'HH:mm:ss.sss'，市场本地
  seq: number;                // 成交序号（用于同时间戳稳定排序）
  price: number;
  volume: number;             // 股
  amount: number;             // 元
  tradeCount?: number;        // 该条包含的成交笔数（3 秒合并分笔才有）
  side: 'B' | 'S' | 'N';      // 归一化：主动买 / 主动卖 / 未知或中性
  rawSide?: string;           // 原始值，如 'M' / 'C' / '1' / '4' / 'F'
  sideSource?: string;        // 'SSE.TradeBSFlag' / 'TX.detail' / 'EM.f55'
  buyOrderNo?: number;
  sellOrderNo?: number;
  channelNo?: number;
  phase?: 'auction' | 'continuous' | 'afterHours';
  granularity: 'tick' | 'merged3s';  // 明确区分交易所逐笔与公开合并分笔
}

/** 逐笔委托 */
interface OrderTick {
  timestamp: number;
  seq: number;
  price: number;
  volume: number;             // 股
  side: 'B' | 'S' | 'N';
  rawSide?: string;           // 深市可能是 '1'/'2' 或 'B'/'C'/'BS' 标识串
  orderType: 'add' | 'cancel' | 'market' | 'limit' | 'bestOwn' | 'unknown';
  rawOrderType?: string;      // 'A' / 'D' / 'U' / '1' / '2'
}

/** 十档快照 */
interface DepthSnapshot {
  timestamp: number;
  bids: { price: number; volume: number; orderCount?: number }[];   // 10 档
  asks: { price: number; volume: number; orderCount?: number }[];
  phaseCode?: string;
}

/** 副图通用输出契约 */
interface PaneSeries {
  paneId: string;
  name: string;               // 'VOL' | 'AMOUNT' | 'VOL_RATIO' | 'MACD' ...
  type: 'bar' | 'line' | 'histogram' | 'horizontalBar';
  series: { time: number; value: number | number[] }[];
  precision?: number;
  shareAxis?: 'x' | 'priceY'; // 筹码峰用 priceY
}

/** 扩展后的数据集 */
interface ChartDatasetV2 {
  symbol: string;
  tradeDate: string;
  market: 'CN' | 'HK' | 'US';
  timezone: string;
  adjust: 'none' | 'qfq' | 'hfq';
  session: { open: string; close: string }[];
  preClose: number;
  floatShares: number;                     // 流通股本（换手率/筹码峰需要）
  bars?: Bar[];
  points?: IntradayPoint[];
  panes?: PaneSeries[];
  auction?: AuctionPoint[];
  chips?: ChipHistogram | ChipStat;
  depth?: DepthSnapshot[];                 // 按需加载
  trades?: TradeTick[];                    // 按需分页加载
  orders?: OrderTick[];                    // 按需分页加载
  source: string;
  updatedAt: string;
}
```

## 7. 对组件架构的影响

| 需求 | 架构影响 |
|---|---|
| 主图 + 多副图 | 需要 `pane` 布局管理器：共享 x 轴、十字光标联动、统一时间→索引映射、可插拔副图注册表 |
| 筹码峰 | 新增第 4 种 pane 类型：横向柱状、与主图**共享价格 y 轴**、缩放需双向同步；历史回看需按日期存多份直方图 |
| 集合竞价 | 独立时间轴（9:15–9:25 / 14:57–15:00），不能塞进常规 240 点分时数组；竞价期间「价有量无」需特殊渲染 |
| 交易明细 | 虚拟滚动表格 + 与图表 crosshair 联动（点 K 线/分时定位到对应时间段明细）+ 分页加载 |
| 十档盘口 | 可选快照回放，按时间戳对齐逐笔；注意快照 3 秒与逐笔毫秒粒度差 |
| 数据量 | 三层加载：静态主图数据（一次性）→ 聚合副图数据（按日）→ L2 明细（按需分页），各层独立缓存 |
| 复权 | 筹码峰、量比、资金流都受复权口径影响；建议数据集锁定单一 `adjust`，切换时整体重载 |

## 8. 新增坑点 Checklist

| # | 坑 | 依据 |
|---|---|---|
| 1 | 把 `C` 当成通用的「主动买/卖/中性」 | 通达信深市标识串里 `C` 是撤单；沪市撤单是 `OrdType='D'` |
| 2 | 认为集合竞价成交有 B/S 方向 | 交易所不打 BS；实测腾讯却给 `09:25:02` 标 `S`、东财给 `15:00:02` 标 `1`，属供应商填充 |
| 3 | 用集合竞价成交算主力净流入 | 无主动方向，结果无意义 |
| 4 | 把公开 3 秒合并分笔当 L2 逐笔 | 东财/腾讯明细一条含多笔成交，粒度完全不同 |
| 5 | 忽略 `TradeBSFlag` 起始日期 | 沪市 2021-04-26 之后才有，更早历史需推断 |
| 6 | 深市套用沪市 BS 字段 | 深市用 `ExecType(4/F)` + `Side(1/2/G/F)`，无主动性字段 |
| 7 | 价格缩放不一致 | SDK 层常见沪市逐笔价格 `/1000`、深市 `/10000`，必须抽样验证 |
| 8 | 时间精度混用 | 沪市成交百分之一秒（14 位）、沪市委托毫秒（17 位）、深市消息序号，合并排序会错乱 |
| 9 | 成交金额精度变更 | 上交所 2023-06-01 起由 2 位改 3 位精度 |
| 10 | 竞价期间把虚拟撮合价当真实成交 | 盘前分时 09:15–09:25 成交量为 0 |
| 11 | 筹码峰当作交易所数据 | 无官方字段，是建模估算；不同软件结果不同 |
| 12 | 筹码峰与 K 线价格轴不对齐 | 横向柱状需共享 priceY，且复权切换要重算 |
| 13 | 流通股本用静态单值 | 换手率、筹码峰会因增发/解禁失真 |
| 14 | 量比缺前 5 日数据 | 量比必须依赖历史分钟/日量，不能只靠当日分时 |
| 15 | L2 明细全量塞进前端 | 单日 GB 级，必须分片 + 预聚合 + 虚拟滚动 |
| 16 | 副图混用不同数据源 | 单位、复权、方向口径不同会互相矛盾 |

## 9. 待确认事项 / 下一期建议

1. **目标市场**（A 股沪市 / 深市 / 港股 / 美股）：直接决定 B/S/C 语义、集合竞价规则、盘后时段、涨跌颜色。建议第一期先把市场范围定死。
2. **Level2 历史数据来源与授权**：交易所历史 L2 为付费授权数据（CSV 文件包）；公开接口只有 3 秒合并分笔。需要确认产品是「用公开分笔做明细演示」还是「必须真 L2 逐笔」——这决定数据采购与后端架构。
3. **筹码峰深度**：只展示按日统计指标（9 列）即可，还是必须画出 150 档完整直方图（含历史某日回放）？后者需要自研计算与预计算流水线。
4. **集合竞价图范围**：只做开盘 9:15–9:25，还是含收盘 14:57–15:00；是否需要「竞价委托」而非仅虚拟撮合价。
5. **副图可配置性**：固定几个副图，还是用户可增删/排序？影响 `PaneSeries` 注册表设计。
6. **是否需要十档盘口 / 委托队列回放**：若需要，数据量与授权成本再上一个台阶。
7. 建议下一期做：统一数据模型定稿 → 静态样例数据集（含 K 线、分时、竞价、筹码峰、模拟逐笔）→ 组件 pane 布局与 crosshair 联动的接口设计。
